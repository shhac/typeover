# 30 — Yaegi upstream tracker (2026-05-21)

Single source of truth for what our vendored Yaegi build CAN'T
do, why, and what we'd retire when each gap closes upstream. Born
out of the auto-build cycle's Yaegi-focus investigation — the
limitations have been referenced piecemeal across design-docs/23,
/24, /26 but never consolidated.

## What we vendor

- **`runtime/yaegi-wasm/go.mod`**: `github.com/traefik/yaegi v0.16.1`
- **Release date**: 2024-04-03 (the LATEST Yaegi release on GitHub
  as of this writing)
- **Notable changelog entry**: v0.16.0 (2024-03-05) added "support
  go1.22"; v0.16.1 only contains two bug fixes (closure memory
  leak; assign-to-blank-var panic). No newer version exists.
- **Build path**: `pnpm runtime:build` → `runtime/yaegi-wasm/build.sh`
  → `GOOS=js GOARCH=wasm go build -ldflags=-s -w -trimpath -o
  public/yaegi/yaegi.wasm .`. Symbol map composed from
  `runtime/yaegi-wasm/symbols/*.go` (each generated by
  `yaegi extract <pkg>`).

## Confirmed limitations (re-probed 2026-05-21)

Run `node runtime/yaegi-wasm/matrix.mjs` for the full probe set;
the three load-bearing gaps are:

### 1. Generic stdlib unavailable

- **Probe:** `import "slices"; slices.Sort([]int{3,1,2})` →
  `undefined selector: slices.Sort`
- **Root cause:** `yaegi extract slices` emits an empty symbol
  map because every exported `slices` function is generic
  (`func Sort[S ~[]E, E cmp.Ordered](x S)`), and Yaegi's symbol
  extractor doesn't yet support generic-typed exports.
- **Upstream:** [yaegi#1704](https://github.com/traefik/yaegi/issues/1704)
  (open since 2025-08-11; no maintainer ETA; no PR in flight).
- **Workaround:** content uses pre-generics path (`sort.Ints`,
  `slices.Index` — non-generic; `slices.Contains` IS supported).
  `design-docs/23` slot 11 uses `alternateCanonicals` to ALSO
  accept the modern `slices.Sort` form via text-match while
  Yaegi runs the canonical `sort.Ints` form.
- **What retires when fixed:**
  - `design-docs/23` follow-up #2
  - The `alternateCanonicals` entry on
    `src/content/exercises/collections/arrays-and-slices/11.yaml`
    (canonical flips to `slices.Sort`; `sort` import drops)
  - The `successNote` on the same slot

### 2. Go 1.22 `range over int`

- **Probe:** `for i := range 5 { fmt.Println(i) }` →
  `panic: nil type` at parse time
- **Root cause:** Yaegi v0.16.0 claims "support go1.22" but the
  range-over-int form isn't wired in. The parser hits the
  expression-as-range-target codepath and bottoms out.
- **Upstream:** no specific issue found; folded into the
  general "Go 1.22 parity" gap.
- **Workaround:** `design-docs/23` Theme 2.3 slot 6 stays MCQ
  (recognition) instead of fill-line (production) — the
  learner sees the modern `for i := range N` form but doesn't
  have to run it.
- **What retires when fixed:**
  - The MCQ-vs-fill-line decision on
    `src/content/exercises/collections/iteration/06.yaml`
    (could become fill-line once the form runs)
  - The author's note inside that file's `notes:` block

### 3. Go 1.22 loop-variable per-iteration fix

- **Probe:** `for _, x := range xs { fns = append(fns, func()
  int { return x }) }` — closures observe a SHARED `x` across
  iterations, producing `3,3,3` instead of `1,2,3`.
- **Root cause:** the language fix lives in Go 1.22's spec;
  Yaegi runs pre-1.22 semantics regardless of the host Go
  version (the interpreter has its own loop-variable model).
- **Upstream:** no specific issue; same "Go 1.22 parity" bucket.
- **Workaround:** `design-docs/26` Theme 2.3 slot 10 uses the
  pre-1.22 `x := x` shadow workaround as the Yaegi-runnable
  canonical AND accepts the modern (shadow-less) form via
  `alternateCanonicals`. Slot's `successNote` explains the
  Yaegi pre-1.22 simulation.
- **What retires when fixed:**
  - The `alternateCanonicals` + `successNote` on
    `src/content/exercises/collections/iteration/10.yaml`
  - The canonical flips to the modern form
  - The `notes:` block paragraph about Yaegi's pre-1.22
    simulation

### User-defined generics ✓ (probed 2026-05-21)

Big finding for Module 4.2 authoring. Yaegi DOES support
user-defined generics — the limitation is exclusively in the
STDLIB extraction path (`yaegi extract slices` emits empty for
generic exports). User code with generic functions, generic
structs, custom constraint interfaces, and `~T`
underlying-type constraints all RUN correctly.

Probes that passed:
- `func Max[T int | float64](a, b T) T { ... }` — type-set
  constraint
- `type Stack[T any] struct { items []T }` with generic
  methods (Push / Pop)
- `type Ordered interface { ~int | ~float64 | ~string }` +
  `func Min[T Ordered](a, b T) T { ... }` — custom
  constraint package shape

#### Quirk surfaced 2026-05-21 (Module 4.2 authoring)

Yaegi's type inference for type-set-constrained generics
DOESN'T propagate from untyped constants the way real `go build`
does. Concrete repro:

```go
type Ordered interface { ~int | ~float64 | ~string }
func Min[T Ordered](a, b T) T { if a < b { return a }; return b }
func main() {
    fmt.Println(Min(2.1, 1.5))           // FAILS: "untyped float does not implement main.Ordered"
    fmt.Println(Min[float64](2.1, 1.5))  // WORKS
}
```

Real Go 1.21+ infers `T = float64` from the untyped float
literals; Yaegi requires the explicit type argument.

**Workaround:** when authoring a generic exercise that uses a
constrained type parameter AND passes untyped constants, write
the call with the explicit type argument (`Min[float64]` rather
than bare `Min`). Captured in `interfaces/generics/09.yaml`'s
notes. No alternateCanonicals needed — the explicit form is
valid Go too.

**What retires when fixed:** the explicit-type-arg form on slot
9 of `interfaces/generics` can re-inline to bare `Min(2.1,
1.5)`. Single-character edit per call site.

Practical impact: Module 4.2 (`interfaces/generics`) can be
authored end-to-end with runnable canonicals — same fill-line +
freeform shape as the rest of the curriculum, no
alternateCanonicals workaround needed for the bulk of the
theme. The only Module-4.2 slots that would need the workaround
are ones that try to USE the generic stdlib (slices.Sort,
maps.Keys, etc.); those slots either reach for the pre-generics
equivalent or stay MCQ-recognition.

#### Quirk surfaced 2026-05-21 (Module 5.3 authoring)

Same root cause as the `errors.As` user-type quirk: **type
SWITCH on user-defined types falls to default** in Yaegi.
The `case *MyType:` branches don't match even when the
interface value's dynamic type IS `*MyType` (probed twice,
confirmed). Type ASSERTIONS (`v.(T)` single + comma-ok)
work fine on user-defined types.

The dividing line: anything going through Yaegi's
reflection-bridge to match user-defined types against case
lists or `errors.As` targets hits this. Single-value and
comma-ok type assertions use a different code path and work.

**Workaround:** for productive type-SWITCH slots, use stdlib
types (`*strconv.NumError`, etc.). For user-defined
custom-error-type exercises, use comma-ok TYPE ASSERTION
instead of type switch. Slot 8 of `errors/type-assertions`
uses comma-ok on `*ValidationError` (works); slots 7 + 9
use type-switch with `*strconv.NumError` (works).

**Author tip:** Yaegi enforces unused-variable in
switch-bound vars more strictly than real Go — a `case`
that doesn't use the bound `e` may need `_ = e` in the
default branch.

**What retires when fixed:** the stdlib-type lean in
`errors/type-assertions` slots 7 + 9 can swap to user-defined
types; the `_ = e` guard in slot 9's default can drop.

#### Quirk surfaced 2026-05-21 (Module 5.2 authoring)

`errors.As` works cleanly with STDLIB error types
(`*strconv.NumError`, `*os.PathError`, `*net.OpError`) but
FAILS on Yaegi-defined custom error types with messages like
"`*target must be interface or implement error`" or "`reflect:
Call using struct { X... } as type error`". The issue is
Yaegi's reflection bridging — yaegi-internal struct types
don't satisfy the interface check that `errors.As` runs
through reflect.

**Workaround:** when authoring an `errors.As` exercise that
needs to be runnable, use a STDLIB error type as the
extraction target (slots 7 + 9 of `errors/is-and-as` use
`*strconv.NumError`). The API shape is identical; the lesson
lands the same.

For exercises that NEED a custom error type, drop to MCQ /
recognition only (no `runtime: yaegi`).

**What retires when fixed:** the `*strconv.NumError` lean in
`errors/is-and-as` slots 7 + 9 can swap to a user-defined
type. Author flag: grep `errors/is-and-as` for "strconv.NumError"
and review whether the use is pedagogical (keep) or
workaround-driven (swap).

`errors.Is` works fine with both stdlib and user-defined
sentinels — no workaround needed there.

## What we'd do differently if a Yaegi PR landed

The `alternateCanonicals` infrastructure (shipped commit
`d2084ac`) was designed so the canonical can flip without a
schema change. Per-slot retirement is a one-line YAML edit (drop
the `alternateCanonicals` + `successNote` fields, swap the
canonical to the modern form). The infra stays — future
generations of "modern Go feature lands but Yaegi lags" will
follow the same pattern.

## Forking is not the answer (yet)

It's tempting to fork Yaegi and add generic-stdlib support
ourselves. We're not going to because:

1. **The fix is upstream-tracked.** Issue #1704 is on the
   maintainers' radar. A fork bifurcates maintenance forever;
   the right move is to wait + contribute a PR if the
   maintainer signals interest.
2. **The maintenance surface is large.** Adding generic
   support to Yaegi's symbol extractor is a structural change
   touching how types are resolved at parse time. Not a
   weekend patch.
3. **Our workaround already serves the learner.** The
   `alternateCanonicals` path means a learner who types the
   modern form gets accepted; they see the modern canonical in
   the `successNote`. The only "missing" experience is being
   able to RUN the modern form and see its actual output —
   which is a degraded affordance, but not a content gap.

## Re-probe cadence

When you bump the Yaegi version in `runtime/yaegi-wasm/go.mod`:

1. Run `pnpm runtime:build` to rebuild the WASM blob.
2. Run `node runtime/yaegi-wasm/matrix.mjs` (the probe matrix
   that backs this document).
3. Re-probe the three gaps above (the `/tmp/probe-yaegi-gaps.mjs`
   shape used in this tick — code embedded in section 1-3 above).
4. If any gap now passes, update this document AND retire the
   matching workaround per the "what retires" notes above.
