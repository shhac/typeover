# 16 — UX review (2026-05-20)

> Reviewer: senior UX designer, bad mood. Persona note: optimised
> for catching what devs miss, not for praise.

## Headline

The site is a series of dev-built scaffolds shipped to learners as if
they were product. The unifying failure is that **state changes have
no learner-facing narrative**: the WASM runtime downloads silently,
the exercise jumps into "Submit" without telling you what Submit is
about to grade, the BlankInput leaks the answer width, the breadcrumb
"Foundations" badge dumps you back to the entire curriculum, the
hint button hits its cap with a passive-aggressive "No more hints",
and the share button on completion fires `navigator.share` without a
single word of pre-flight context. None of these are "bugs" in the
test-coverage sense — every one of them is the kind of paper cut
that makes a real human close the tab on exercise 3.

## Findings

### F-1. The persistent header says "curriculum →" — and that's the only chrome on every page
**Where**: `/` (header suppressed) + every other page; `src/layouts/BaseLayout.astro:108-130`
**What you see**: A first-time visitor on `/go` who clicks "curriculum →" is already on `/go` — the link is suppressed at runtime but only after they've scanned for it. A returning learner who wants to *get to a specific exercise* has no global "Jump to where I was" affordance. The header is a brand strip and one outbound link; there's no module/theme switcher, no "resume", no in-page TOC.
**Why it's bad**: The whole site funnels through one page (`/go`) and one accordion. If you're four themes deep you have to: click `Foundations` badge (lands on /go), scroll, hunt the right theme, click overview, click your exercise. Three clicks and a scroll, every time.
**Suggested fix**: Either a "Resume — Loops · ex 04" link in the header (reads last touched exerciseId from localStorage) or a left-rail TOC of themes that persists across exercise pages.
**Severity**: major

### F-2. Breadcrumb "Foundations" badge is a lie
**Where**: theme overview + exercise pages; `src/pages/go/[module]/[theme]/index.astro:66-72`, `[index].astro:89-95`
**What you see**: Every learner page shows `[Foundations] → [Theme name]` at the top, where `Foundations` looks like the module name and reads as "click here for the module overview." Clicking it lands on `/go` — the entire site curriculum index, scrolled to the top. There is no `/go/foundations` route.
**Why it's bad**: The badge promises a level-up navigation that doesn't exist. The aria-label says "Up to curriculum (Foundations)" which only confirms the dev knew it was wrong and papered over it. Users learn quickly that the breadcrumb lies and stop trusting it.
**Suggested fix**: Either ship a real `/go/foundations` module overview (preferred, since `/go` is a 10-screen wall) or rename the badge to "Curriculum" so it matches its destination.
**Severity**: major

### F-3. BlankInput width leaks the answer length
**Where**: `src/components/exercise/BlankInput.tsx:101-108`
**What you see**: `width: ${Math.max(expected.length + 4, 5)}ch`. A blank for `nil` is ~7ch wide; a blank for `!=` is ~6ch wide; a blank for `errors.New("divide by zero")` is ~31ch wide. The input visually pre-announces "this answer is 3 chars / 2 chars / a giant expression".
**Why it's bad**: A learner can guess the answer category from the width alone. On the conditionals fill-word that asks for `!= nil`, the two boxes are visually almost equal width, telegraphing "short operator, short literal." The whole point of fill-word is producing the recall — you've stripped it.
**Suggested fix**: Fix the input to a single column-stable width (say 14ch) and let it scroll or grow on overflow. Anything but `expected.length`.
**Severity**: major

### F-4. Yaegi loads with zero loading UX on first Run
**Where**: `src/components/exercise/Freeform.tsx`, `FillBlankLineInput.tsx`; runtime in `src/runtime/index.ts`
**What you see**: On a learner's first freeform / fill-line exercise, the Run button is enabled, says "Run", and looks normal. Clicking it triggers a ~1.9 MB brotli WASM download. The button flips to "Running…" but there's no "Loading runtime…" pre-state, no progress bar, no warning that the first run is heavy. If the network's slow they think the button is broken.
**Why it's bad**: First-run cost is the make-or-break moment for any code-runner UI. We hide it entirely. Worse, MCQ and fill-word pages never load Yaegi — so a learner whose first freeform happens at exercise 08 of a theme suddenly experiences a 4-second lag and assumes their browser hung.
**Suggested fix**: Preflight the runtime when the exercise mounts with a visible "Booting Go runtime… ~2 MB, one time" badge. Disable Run until ready. Cache the WASM in service worker so the second exercise is instant.
**Severity**: major

### F-5. Hint button caps at "No more hints" — a dead button shouting at you
**Where**: `src/components/ds/HintButton.tsx:46-49`
**What you see**: After three clicks the button reads `No more hints`, stays visible, stays disabled. It now occupies real estate and is permanently telling the learner they've exhausted help.
**Why it's bad**: The wording is faintly punitive ("you've used them all up"), and the button no longer does anything. It should either collapse, change role ("Reveal canonical →"), or remove itself.
**Suggested fix**: After hint 3, swap the button for a quiet "Hints exhausted — try Reveal canonical →" link that actually does something. Or collapse the button entirely.
**Severity**: minor

### F-6. "Reveal correct" silently records the exercise as a failure
**Where**: `src/lib/exercise-phase.ts:92-95`
**What you see**: The "Reveal correct" button in the wrong-phase looks like a help affordance ("show me the answer"). Clicking it calls `recordInstanceFailed` — the exercise is logged as failed against your progress with no warning.
**Why it's bad**: A learner who's stuck and wants to peek at the canonical to learn from it gets penalised in their progress stats. The dev knows this is "pinned behaviour" (see comment). The learner does not. There's no "this will count as a fail" disclosure on the button.
**Suggested fix**: Either change the copy to "Give up — reveal answer (counts as fail)" or stop counting reveals as failures and only count an explicit "Skip this exercise" as a fail.
**Severity**: major

### F-7. Share button fires `navigator.share` with no preview of what's being shared
**Where**: `src/components/completion/ModuleCompleteCard.tsx:206-219`
**What you see**: Button labelled `Share`. Click it and your OS share sheet pops up with text + URL pre-filled. You never see what the text says before the sheet opens. Cancelling the sheet silently resets state (you have to click Share again to see what would have been sent).
**Why it's bad**: People are careful about what they post. A "Share" button that immediately invokes the OS share sheet without showing the payload is hostile to a cautious user. They want to read it first, maybe edit, then post.
**Suggested fix**: Render the share text and URL above the button (read-only), then "Share" / "Copy". Even better: let the learner edit the text before sharing.
**Severity**: major

### F-8. Module-complete "almost there" view is reachable by URL but has no nav out
**Where**: `/go/<module>/complete`; `src/components/completion/ModuleCompleteCard.tsx:139-177`
**What you see**: A learner who types `/go/foundations/complete` (or follows a stale link) before completing the module sees the "almost there" view listing per-theme progress. There is no Continue button, no Back-to-curriculum button, no link to the first unfinished exercise. The only nav is the per-theme links in the list — which all go to theme overviews.
**Why it's bad**: A learner is told what they haven't done but isn't given a "Go finish your next one" action. The complete-path view has a Continue button; the almost-there view doesn't. Inconsistency between two states of the same screen.
**Suggested fix**: Compute the first unfinished exerciseId on this branch too and render a `[Continue with N→]` primary button.
**Severity**: major

### F-9. Settings page mismatches its own copy and exposes four axes labelled as four but headed as one
**Where**: `/settings`; `src/pages/settings.astro:26-35` + `src/components/settings/AppearancePicker.tsx`
**What you see**: The page lead reads `Four axes — pick what reads best for you`. There's a single H2 "Appearance" above a stack of 4 unlabelled radio-group sections (Theme / Density / Corners / Style). Each section has only a tiny mono-uppercase eyebrow as its title. The "preview" is the first thing rendered but isn't called out — the learner sees a panel of buttons, then four radio walls, no separators.
**Why it's bad**: 15+ radio options stacked is decision paralysis. There's no "Defaults" reset button, no "show me what this changes" tooltip per row, and the Style axis has five options whose visual differences (Cardboard, Textbook, Glass, Islands) are not previewed at the option-level — you have to pick each one to see what it does.
**Suggested fix**: One H2 per axis (use the actual section labels), add a "Reset to defaults" button, and consider mini-thumbnails per Style option. Also: the "Four axes" copy doesn't match the page's actual layout — fix the lead.
**Severity**: major

### F-10. Empty-progress state on /go and theme pages is a void
**Where**: `/go`; `/go/<module>/<theme>`; `src/pages/go/index.astro` + `[theme]/index.astro`
**What you see**: A fresh learner who lands on `/go` sees no "Start here" call-to-action above the fold beyond a generic intro. The curriculum tree is browse-anywhere but offers no recommended path arrow, no Module 1 highlight beyond the accordion being open. On a theme overview with fresh state, the ThemeProgressChip is silently hidden (renders an aria-hidden placeholder), so the row reads `[exercises] [12 ready]` with nothing to anchor where to start.
**Why it's bad**: A first-time visitor with no progress sees no orientation. "Start anywhere" without a strong default is decision paralysis, especially when modules 2-7 are scaffolded shells that the user might click into and hit a wall.
**Suggested fix**: On `/go`, surface a `[Start the first exercise →]` button at the top of an open Module 1 accordion. On theme overview, when no progress exists, replace the silent chip with `[Start exercise 01 →]` as the dominant CTA.
**Severity**: major

### F-11. "Try again with a different instance" / "Different exercise" labels are confusing
**Where**: `src/components/exercise/ExerciseShell.tsx:138, 162`
**What you see**: Wrong phase has buttons `Try again`, `Different exercise`, `Reveal correct`. Right phase has `Try again with a different instance`. "Different exercise" actually doesn't go to a different exercise — it generates a new variant of the same exercise. "Different instance" is dev-speak; learners don't know what an "instance" is.
**Why it's bad**: "Different exercise" reads as "navigate me to the next lesson" — a learner would expect to leave this page. Instead it reshuffles the template. Same content, different button copy. The right-phase "Try again with a different instance" reads as "do it again", but the user has just succeeded — why would they retry?
**Suggested fix**: "New variant" or "Reshuffle this exercise" for both. Drop the word "instance" from learner copy entirely.
**Severity**: major

### F-12. Mobile keybar is permanently fixed at the bottom on /go and /settings
**Where**: `src/components/ds/MobileKeyBar.tsx:118-130`; only rendered inside Freeform / FillBlankLineInput
**What you see**: Actually only renders on exercise pages — but Lighthouse will flag the `z-50` fixed bar overlapping content if the page is short. More importantly, on a mobile freeform exercise the bar covers the bottom 44px of content; if the Run-result panel appears below the input, it lands behind the keybar and needs scrolling to reveal.
**Why it's bad**: On a short exercise the Run result is hidden behind the keybar. Learners think Run didn't work.
**Suggested fix**: Add `padding-bottom: 56px` to the exercise container on mobile when the keybar is present so result text never sits behind the bar.
**Severity**: major

### F-13. CodeBlock with "your turn — fill the blanks" filename strip is read as a tab, not an instruction
**Where**: `src/components/exercise/FillBlankWord.tsx:90`, `FillBlankLineInput.tsx:121`
**What you see**: Filename strip says `your turn — fill the blanks` or `your turn — type the line`. It's styled like every other filename label on the site (used for `users.ts`, `users.go`). A reader will parse it as a filename, not an instruction.
**Why it's bad**: Instructions disguised as filenames don't register as instructions. The actual instruction (prompt) is two visual blocks up — by the time the learner reaches the input, the prompt is off-screen on mobile.
**Suggested fix**: Promote "your turn" copy to a small instruction line outside the CodeBlock filename slot, e.g. `[Fill in the blanks →]` above the codeblock. Reserve the filename strip for actual filenames.
**Severity**: minor

### F-14. RunResultPanel shows `expected "1\n2\n3\n4\n5\n"` as a JSON-stringified blob
**Where**: `src/components/exercise/RunResultPanel.tsx:24-26`
**What you see**: The "expected" line literally renders `expected "1\n2\n3\n4\n5\n"` with escaped newlines because it uses `JSON.stringify`. Same line then renders the actual stdout as raw multi-line text. So learners compare a one-line JSON string against a multi-line stdout block — the comparison is by-eye and across formats.
**Why it's bad**: It's a debugging readout, not a learner readout. Real users have to mentally parse `\n` back into newlines to verify their output matched.
**Suggested fix**: Render expected as a real `<pre>` block beside actual stdout, with green/red borders. Side-by-side "what you got" vs "what we wanted".
**Severity**: major

### F-15. Settings: changing theme has no confirmation, no undo
**Where**: `src/components/settings/AppearancePicker.tsx:64-67`
**What you see**: Click "Light", the entire site flashes to light. No "Reverted" affordance, no undo, no "Saved" toast. If you don't like it you have to click the previous radio to revert — and the radio styles in light mode might be unreadable to you.
**Why it's bad**: Settings that apply instantly and irreversibly with no feedback are stressful. A learner with a vision impairment who accidentally picks "Light" or "Pill" and finds it unreadable can't easily back out.
**Suggested fix**: Quiet "Saved · undo" toast at the bottom-right that auto-dismisses in ~5s. Or a one-button "Reset to defaults".
**Severity**: minor

### F-16. No 404 page
**Where**: missing; nothing in `src/pages/404.astro`
**What you see**: Visit `/go/foundations/loops/99` (no such exercise) or `/go/non-existent-module` and you get the host's stock 404 (Vercel/Netlify default), branded as the host, not as typeover. No back-to-curriculum, no "did you mean…".
**Why it's bad**: A stale link from a shared URL or a typo dumps the user out of the experience entirely.
**Suggested fix**: A minimal `src/pages/404.astro` with the brand, a "back to curriculum" link, and the curriculum index linked inline.
**Severity**: major

### F-17. Footer "github" link doesn't open in new tab; site is build-in-public, learner loses their place
**Where**: `src/layouts/BaseLayout.astro:170-176`
**What you see**: The footer has `github` linked to the repo with `rel="noopener noreferrer"` but no `target="_blank"`. Click it mid-exercise and you navigate away — your progress signals are preserved but your scroll, focus, and input state are not.
**Why it's bad**: Build-in-public is a value-add link; it shouldn't cost the learner their session. Same applies to the privacy GitHub link.
**Suggested fix**: `target="_blank"` on external links. Add a tiny `↗` glyph so the affordance is visible.
**Severity**: minor

### F-18. The Run button can be clicked when canSubmit is false — but the UI doesn't tell you why
**Where**: `src/components/exercise/FillBlankLineInput.tsx:58`, `Freeform.tsx:68`
**What you see**: For fill-line, `canSubmit` requires `yaegi.runResult() !== null && !running && input().trim() !== ""`. The Submit button is disabled until you Run first — but the disabled state shows no tooltip, no explanatory text. A learner types the answer and presses Submit. Nothing happens. No "Run first" hint anywhere.
**Why it's bad**: Disabled buttons with no explanation are the canonical UX antipattern. The user feels broken.
**Suggested fix**: When Submit is disabled, render a small hint next to it: `[Run your code first →]`, or auto-Run on Submit when no result exists.
**Severity**: major

### F-19. Auto-indent in freeform textarea but no syntax highlighting, no bracket-match, no autocomplete
**Where**: `src/components/exercise/Freeform.tsx:113-132`
**What you see**: Plain `<textarea>`. The roadmap notes "CodeMirror integration replaces the textarea later" but that's later. Today, a learner writing 10+ lines of Go in a plain textarea with no highlighting, no `}` autoclose, no indentation guides — and an auto-indent Enter that's the only smart thing about it.
**Why it's bad**: Code editing in 2026 inside a plain textarea reads as "the dev didn't ship the editor yet." Learners typing freeform Go will make trivial syntax errors the editor would have prevented.
**Suggested fix**: Either ship CodeMirror sooner (it's flagged for #23 — accelerate it) or at minimum add bracket-pairing and a fixed-width font with visible whitespace.
**Severity**: major

### F-20. Hint substitution silently leaves `${var}` placeholders visible when values are missing
**Where**: `src/components/ds/HintButton.tsx:23-26`
**What you see**: `resolveHint` leaves unknown `${name}` placeholders intact when the values map doesn't have them. So if a hint authored for one exercise gets reused on a sibling that has different vars, the learner sees literal `${foo}` in the hint text.
**Why it's bad**: Comment says "lenient — unknown placeholders left as-is so a hint copy-pasted from a sibling exercise doesn't crash, just renders with the placeholder visible (authoring smell that the author will spot)." But the author isn't the one looking at it — the learner is. This is dev-comfort dressed up as a feature.
**Suggested fix**: In dev mode, throw. In prod, strip unresolved placeholders and ship the hint as plain prose, not as a debug string.
**Severity**: minor

### F-21. Long exercise prompt scrolls off-screen as the answer area takes focus
**Where**: any exercise; `src/components/exercise/ExerciseShell.tsx:93-99`
**What you see**: The prompt renders at the very top of the answer panel. By the time a learner scrolls down to fill the blank / type the freeform code, the prompt is off-screen on a laptop and definitely off-screen on mobile. There's no sticky prompt header, no "show prompt" toggle in the toolbar.
**Why it's bad**: Mid-exercise, you forget what exactly was being asked. You scroll up, read the prompt, scroll down, lose the focused input. Several scroll cycles per exercise.
**Suggested fix**: Either sticky the prompt header at the top, or duplicate a one-line synopsis next to the answer region. Especially important for freeform with multi-paragraph prompts.
**Severity**: major

### F-22. The exercise's `type` badge says "fill word" / "fill line" / "freeform" — meaningless to a learner
**Where**: theme overview cards; `src/pages/go/[module]/[theme]/index.astro:120-122` + `src/lib/curriculum.ts:15-20`
**What you see**: Each exercise card on the theme overview shows a small badge like `multiple choice`, `fill word`, `fill line`, `freeform`. These are dev categories. A learner sees `fill line` and `freeform` and can't tell what the actual differences are.
**Why it's bad**: Two of the four type labels (`fill line`, `freeform`) are jargon that have no plain-language meaning to a first-time learner. They look like difficulty levels but they're actually about the input shape.
**Suggested fix**: Either drop the badge (it doesn't help orient the learner — they'll see what kind of question it is when they open it), or rename: `pick one`, `fill blanks`, `type one line`, `write a program`. And consider adding a one-glance difficulty/effort signal instead.
**Severity**: minor

### F-23. Stale code comment: "skip ahead link in the picking-phase footer" — doesn't exist
**Where**: `src/components/exercise/ExerciseShell.tsx:58-60` (comment), no implementation
**What you see**: Internal docs reference a secondary "skip ahead" link in the picking-phase footer that lets the learner advance without solving. It is not rendered. A learner who's stuck has no way to skip forward without either revealing (which logs a fail) or backing out via breadcrumb.
**Why it's bad**: Dev-side, this is doc-rot. Learner-side, the lack of skip + the "Reveal = fail" mechanic + no Back-to-theme button in picking phase means a stuck learner has nowhere to go but backwards (browser back) or down (reveal-and-be-marked-wrong).
**Suggested fix**: Ship the documented skip link in the picking-phase footer ("Skip — try a different exercise →"). Or delete the comment if the design has been retired.
**Severity**: minor

### F-24. Module-complete celebration banner reads "typeover · MODULE COMPLETE" — but Foundations is module 1 of 7
**Where**: `src/components/completion/ModuleCompleteCard.tsx:181-186`
**What you see**: All-caps amber wordmark `typeover · MODULE COMPLETE`. No "1 of 7" framing. The achievement reads as a final-boss screen.
**Why it's bad**: The learner has just finished 1/7 of the Go track (and the other 6 are scaffolded). The triumphalism oversells the milestone, and the "Share" CTA encourages broadcasting "I finished Go!" when they've only done Foundations.
**Suggested fix**: Reframe as `Module 1 of 7 complete · Foundations`. Adjust the share template — `"finished Foundations on typeover"` is honest; the current `"finished {moduleTitle}"` interpolates correctly but the framing around it inflates it.
**Severity**: minor

### F-25. Footer is the only place to find Settings / Privacy on every page
**Where**: `src/layouts/BaseLayout.astro:142-178`
**What you see**: Settings and Privacy are footer-only. A learner who wants to change theme has to scroll the entire page to the bottom. The persistent header has the brand and a `curriculum →` link only.
**Why it's bad**: Settings is the most frequently-used non-exercise route. Burying it in the footer means a learner who realises mid-exercise that the contrast is wrong has to scroll out of their focus to fix it.
**Suggested fix**: A small icon/text link in the header strip (top-right beside `curriculum →`). Or expose theme-toggle directly in the header.
**Severity**: minor

## Anti-patterns we should rule out

Patterns that recurred across findings — should land in the DS / authoring contract so the same shape of mistake doesn't sneak back in.

- **Dev-vocabulary in learner UI.** "Instance", "fill-line", "fill-word", "different exercise (means: reshuffle)", "Stop / reset runtime", "No more hints", "expected `\"foo\\n\"`". Every internal noun has been published verbatim. Rule: every string a learner sees gets passed through a "would my mum understand this" filter before merge.
- **Disabled buttons with no explanation.** Submit on fill-line / freeform disables until Run runs, Hint disables after 3 clicks, Run disables when input is empty — none of them explain why. Rule: a disabled button always renders a hint adjacent to it explaining the gating condition.
- **State changes with no acknowledgement.** Theme switch, share fired, settings saved, exercise variant reshuffled — all happen instantly with zero confirmation. Rule: every action that mutates persistent state shows a brief acknowledgement (toast, label flip, sentence change). The Feedback component already exists; use it.
- **Affordances that aren't.** BlankInput width = answer length (information leak). Filename strip used for instructions (semantic abuse). Breadcrumb badge that goes somewhere else (lie). Rule: a visual primitive does one thing — when it starts pulling double duty, split it.
- **No empty-state design.** Fresh /go is a flat tree with no "start here". Fresh theme overview hides the progress chip but renders an invisible placeholder. Fresh exercise pages give no breadcrumb sense of "this is your first exercise." Rule: every list-rendering surface has a designed empty state, not "render the chrome but hide the data."
- **Heavy assets with no preflight.** Yaegi loads 1.9 MB brotli on first Run with no indicator. Google Fonts load synchronously. Rule: any > 50 KB asset that's load-on-demand needs a visible preflight; any blocking asset needs a fallback.
- **Penalties dressed as help.** "Reveal correct" records a fail without telling you. Rule: any progress-affecting action discloses its consequence in the button label.
- **Triumphalism scoped to the wrong unit.** Module-complete celebration treats 1/7 as the whole track. Rule: completion messaging proportional to what was actually completed.
- **Documentation comments as a substitute for shipped UX.** "skip ahead link in the picking-phase footer" — documented, not built. Rule: comments that describe UX are tested against the rendered UX, not assumed.
