## Headline

The biggest compounding problem is **naming drift around the four
appearance axes** combined with **localStorage progress reads with
zero memoisation across N island instances per page**. Both are
the kind of "fine today, miserable in three months" rot — a fifth
style value will land in `STYLES`, BaseLayout's inline bootstrap
will silently fall back to default and no test will tell you;
meanwhile every theme-overview render parses the progress blob
`O(themes × exercises)` times because each chip is its own island
calling its own un-cached `read()`. The DS layer also has a
half-finished feel: `_internal.ts` claims to be DS-private but
two `exercise/` components reach in via relative path, `cn` is
the only thing in there, `<Heading>` is overridden with
`class="!text-2xl"` in three places (proof the size scale is
wrong for those level-2 uses), and the new primitives
(`Eyebrow`, `Compare`, `MobileKeyBar`, `ProgressChip`, `TrackCard`,
`Accordion`) are missing from both the `/design-system` inventory
page AND the `a11y.test.tsx` gate that "blocks launch".

## Findings

### F-1. Four names for one axis: shape / radius / corners / pill
**File**: `src/lib/theme.ts:103-128`, `src/components/settings/AppearancePicker.tsx:264`, `design-docs/13`
**What's wrong**: The "shape" axis from the design docs is called `RADII`/`RadiusId`/`currentRadius`/`setRadius`/`RADIUS_STORAGE_KEY`/`data-radius` in code, "Corners" in the settings UI, and "shape" in `design-docs/13`. The `theme.ts` header comment also still says `sharp | normal | rounded` but the enum has four values (pill was added).
**Why it matters**: Author searching for "shape" finds nothing in code; reviewer searching for "Corners" finds only UI strings; new contributor adds a 5th option to `STYLES`, forgets the matching string-literal list in `BaseLayout.astro`'s bootstrap, and gets a silent default.
**Suggested fix**: Pick one name (I'd take `shape` — matches the design doc — or rename the doc to `radius` and be done), apply it across symbol names, storage keys, data attributes, UI labels, and the file header.
**Severity**: major

### F-2. BaseLayout bootstrap duplicates every enum from `theme.ts`
**File**: `src/layouts/BaseLayout.astro:35-78` vs `src/lib/theme.ts:23-155`
**What's wrong**: The inline pre-paint script hard-codes `"dark"|"light"`, `"compact"|"normal"|"airy"`, `"sharp"|"normal"|"rounded"|"pill"`, and `"terminal"|"cardboard"|"textbook"|"glass"|"islands"`. Add a new style to `STYLES` and the bootstrap will silently coerce it to `"terminal"`. No test catches the drift.
**Why it matters**: The whole point of the bootstrap is "no flash of wrong theme." Drift here re-introduces the flash for the new value and nobody notices until a user reports it.
**Suggested fix**: Generate the bootstrap from the same enums (either inline-fetch a tiny JSON module pre-paint, or `Astro.define`-template the script body with the constants from `theme.ts`, or write a single test that imports both and asserts each enum's members appear literally in the script source).
**Severity**: major

### F-3. `summarizeTheme` and per-exercise islands re-parse the progress blob N+1 times per render
**File**: `src/lib/progress.ts:145-173`, `src/components/progress/{Theme,Exercise}ProgressChip.tsx`, `src/pages/go/[module]/[theme]/index.astro:91-123`
**What's wrong**: `summarizeTheme` calls `getExerciseProgress` per id, each of which calls `read()` — every read JSON-parses + Zod-validates the blob AND mutates an in-memory copy (`exerciseSlot` writes a slot it then throws away). The theme overview also mounts one `ExerciseProgressChip` island per exercise plus one `ThemeProgressChip`, so a 9-exercise theme triggers ~10 islands × independent `read()` calls.
**Why it matters**: Per-page latency scales with theme size, and the Zod schema is non-trivial. The cost is invisible today (9 exercises) but Module 2-7 themes will hit the same path. Also: silently mutating the parsed-but-not-persisted blob inside a "read" function is a footgun for anyone who comes to read this code.
**Suggested fix**: Memoise `read()` for the duration of a render tick (or hand chips a pre-computed snapshot from a shared signal). Make `getExerciseProgress` return `null` for un-touched slots; create-only-on-write is the right shape for a read helper.
**Severity**: major

### F-4. `_internal.ts` contract is broken
**File**: `src/components/ds/_internal.ts:5` vs `src/components/exercise/{BlankInput,McqOption}.tsx:1`
**What's wrong**: The file header says "Not exported from index.ts — these are implementation details, not primitives." Two non-ds files import `cn` via `../ds/_internal`.
**Why it matters**: The "private to DS" rule is what justifies the underscore prefix; the moment exercise components rely on it, the file is part of DS's public surface and the docstring is a lie. Tomorrow somebody refactors `cn` thinking only DS callers exist.
**Suggested fix**: Move `cn` to `src/lib/cn.ts` (it's a stand-alone utility) and import from there everywhere, OR export it from `~/components/ds`. The current half-private state is the worst of both.
**Severity**: major

### F-5. `MobileKeyBar` + `<Freeform>` carry an asymmetric synthetic-input-event sync
**File**: `src/components/exercise/Freeform.tsx:121-149`
**What's wrong**: After `handleAutoIndentEnter`, the comment says "Solid's onInput won't run from a synthetic dispatch here — sync the signal directly" and manually calls `setCode`. Three lines below, `MobileKeyBar.onInsert` calls `insertAtFocused(text)` which fires the same synthetic input event without the manual `setCode`. If the comment is correct, every mobile key tap silently fails to update `code()`, so Run sees stale text. If the comment is wrong, the manual sync in the Enter path is dead defensive code. Either way, one of the two is buggy.
**Why it matters**: This is the mobile-editing happy path. A regression here breaks freeform code-input on the phones the whole MobileKeyBar exists for, and no test covers the round-trip (the test mocks `~/runtime`, not the input→signal→buildProgram chain through MobileKeyBar).
**Suggested fix**: Verify in a real browser. If Solid's onInput does fire on synthetic dispatch (jsdom shows it does — see `textarea-insert.test.ts` line 79), drop the manual `setCode`. If it doesn't, do the same sync after `insertAtFocused` and add a `FillBlankLineInput.test.tsx` that walks Tap-`{`-then-Run end-to-end.
**Severity**: major

### F-6. `useKeyboardInset` is a leak risk and untested
**File**: `src/components/ds/MobileKeyBar.tsx:50-69`, `MobileKeyBar.test.tsx:83-92`
**What's wrong**: Listeners are added to `window.visualViewport` and removed in `onCleanup`, but the test suite has zero coverage that unmount actually removes them (or that `vv` even exists). Without that pin, a future refactor that adds an early-return or reorders the `onMount` chain leaks listeners forever.
**Why it matters**: Each exercise page mounts and unmounts MobileKeyBar at least once; a leaked listener accumulates per nav.
**Suggested fix**: Add a test that stubs `window.visualViewport` with `addEventListener`/`removeEventListener` spies and verifies the cleanup. Also: the `Math.max(0, …)` clamp could be replaced by a single guard for `vv === undefined` early-return; the inset is already a no-op there.
**Severity**: major

### F-7. `theme.ts` uses redundant `as` casts the type guard should narrow
**File**: `src/lib/theme.ts:45, 89, 119, 147`
**What's wrong**: `if (isTheme(attr ?? null)) return attr as ThemeId;` — the guard is `s is ThemeId`, so TS would narrow naturally if called on `attr` directly. The `attr ?? null` argument and the cast back are both required only because of the awkward indirection.
**Why it matters**: CLAUDE.md explicitly prefers `satisfies`/`as const`/typed helpers over `as`. Four near-identical violations in one file is exactly the rot the rule exists to prevent.
**Suggested fix**: Replace with `const attr = document.documentElement.dataset.theme; if (attr !== undefined && isTheme(attr)) return attr;` and update `isTheme` to accept `string | undefined`. Applies symmetrically to density/radius/style.
**Severity**: minor

### F-8. `HintButton` uses an `as` cast for a counter that already has a discrete-union type
**File**: `src/components/ds/HintButton.tsx:41`
**What's wrong**: `setRevealed((r + 1) as 1 | 2 | 3);` — `r` is `0|1|2|3` and capped above to `< 3`, so the cast hides the arithmetic. Could be `r === 0 ? 1 : r === 1 ? 2 : 3` or just type `revealed` as `number` and constrain at the boundary.
**Why it matters**: Compounds with the rest of the `as` casts in the codebase; trains contributors that "type narrowing via assertion" is acceptable.
**Suggested fix**: Either widen the signal type to `number` (the only consumer is `<= 3` comparisons) or write the increment as a narrowing ternary.
**Severity**: nit

### F-9. `format-inline.ts` uses `let` for a single-assignment-chain that should be `const`
**File**: `src/lib/format-inline.ts:50-53`
**What's wrong**: `let s = escapeHtml(text); s = s.replace(...); s = s.replace(...); return s;` — re-assigned only to chain. CLAUDE.md says "Always use `const` — if something needs `let`, restructure the code."
**Why it matters**: The exact pattern the rule exists to push back on. The function is six lines; the chain trivially flattens.
**Suggested fix**: `return escapeHtml(text).replace(INLINE_CODE_RE, ...).replace(BOLD_RE, ...);`
**Severity**: nit

### F-10. `ExerciseShell` non-null `!` assertions after a `<Show>` guard
**File**: `src/components/exercise/ExerciseShell.tsx:148-160`
**What's wrong**: `<Show when={props.nextExerciseHref}>...<a href={props.nextExerciseHref!}...></Show>` and the same for `themeHref`. Solid's `Show` accepts a render-prop form (`<Show when={x}>{(v) => …v()…}</Show>`) that narrows naturally.

**Severity**: minor

### F-11. `RunResultPanel` hides every pane when expectStdout is `""`
**File**: `src/components/exercise/RunResultPanel.tsx:27-49`
**What's wrong**: Every `<Show when={props.result.stdout !== ""}>` predicate collapses on the empty-stdout common case. The content scaffolder (`content-new-theme.mjs`) stamps freeforms with `expectStdout: ""`, so a learner correctly producing empty stdout sees nothing — no confirmation, no panel.
**Why it matters**: As soon as someone uses the scaffolder to stub a M2 theme, the freeform UX silently breaks for the stub. Also the duration line at top renders `expected ""` which looks ugly.
**Suggested fix**: Render a placeholder pane when stdout is empty AND `expectStdout === ""` ("(no output) — matches expected"). Don't gate visibility on truthiness of free-form text.
**Severity**: major

### F-12. `ModuleCompleteCard` recomputes the progress summary inline against a different code path than its own onMount snapshot
**File**: `src/components/completion/ModuleCompleteCard.tsx:56-81, 151-176`
**What's wrong**: `onMount` snapshots the summary into `progress()`; the "almost there" fallback calls `summarizeTheme(theme.exerciseIds)` *again* inside `<For>` for each theme. Two sources of truth, evaluated at different ticks; if localStorage changes between them (it can — `recordHintUsed` fires from `HintButton` mounted in the same tree), the two halves disagree.
**Why it matters**: Subtle state mismatch in the celebration screen — exactly the place that must read clean. Also: every per-theme `summarizeTheme` call inside the For triggers F-3's read fan-out.
**Suggested fix**: Snapshot per-theme summaries in `onMount` and render from the snapshot in both branches. Reactivity isn't needed here — the page is reached on navigation, not in response to live progress updates.
**Severity**: major

### F-25. Yaegi worker registration timing is a single-microtask gamble
**File**: `src/runtime/yaegi-worker.ts:72-82`
**What's wrong**: `void go.run(wasmRes.instance); await Promise.resolve();` then asserts `self.yaegiEval` is a function. The whole load-bearing assumption is that Go's `js.Global().Set("yaegiEval", …)` lands in the first microtask of `go.run`. Holds today; brittle to any Yaegi/wasm_exec upgrade.
**Why it matters**: A future wasm_exec rev that adds one more `then` to its startup will fire the "did not register yaegiEval" error and break every exercise without warning. Hard to diagnose because nothing in the worker says "we picked single microtask deliberately."
**Suggested fix**: Poll for `self.yaegiEval` with a bounded retry (say 200ms with 5ms ticks) before throwing. Same outcome on success, far more robust to startup jitter.
**Severity**: minor

## Patterns to add to the contract

- **No `class="!text-…"` on DS components.** If the size is wrong, fix the component or add a prop. Lint rule: ban `!` Tailwind important-prefix in JSX/Astro class strings outside `src/styles/`.
- **No `as Foo` cast immediately after a type-guard call.** Add an ESLint custom rule / oxlint rule once available; for now, a CONTRIBUTING bullet that `is` guards must be applied to the same expression you read.
- **No commit-hash or "task #N" comments in code.** Reference design-docs/N or inline the rationale. Hashes go stale on squash; task numbers go stale when the task closes.
- **`client:only` and `client:visible` choices must be commented.** Hydration choice is invisible at the component level; the page choosing it owns the rationale.
- **Every DS export in `src/components/ds/index.ts` must appear in `src/pages/design-system.astro` AND `src/a11y.test.tsx`.** Enforce with a test that imports `index.ts` and asserts every exported component name appears in the inventory page source and the a11y test file.
- **`localStorage` reads inside Solid components require memoisation.** No `read()` calls from inside a `<For>` or per-render accessor. Document the pattern: snapshot in `onMount`, read from the snapshot.
- **No structural overlap between `_internal.ts` and outside-of-DS callers.** Either it's private (only DS files import it) or it's public (export from index.ts). Half-state forbidden.
- **Inline bootstrap in BaseLayout cannot duplicate enums.** Add a test that asserts every member of every appearance enum appears as a literal in the bootstrap script source — fails when someone adds a value to one side and not the other.
- **`onCleanup` for `addEventListener` requires a removal test.** Every component that subscribes to `visualViewport` / `matchMedia` / `window` events needs a "unmount removes listeners" pin.
- **JSDoc comments must match behaviour.** A `Shuffle in place` comment over a copying implementation is a bug. Add to PR review checklist; over time these compound.
