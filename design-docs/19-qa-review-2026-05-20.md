# 19 — QA review (2026-05-20)

> Reviewer: senior QA, bad mood. Persona note: optimised for
> the cases the dev didn't think of.

## Headline

The progress-storage layer is the worst class of breakage: a single
corrupt `typeover:progress` blob spawns one fresh
`typeover:progress:corrupt-<iso>` backup **per read**, and one page
load can issue 8–116+ reads (every `getExerciseProgress` call rebacks
up the same blob until the first valid write lands). There is no cap
on backup keys, no de-duplication, and no garbage collection — a
flaky storage extension or a one-off DevTools paste will eventually
fill the 5 MB localStorage quota and start failing silently. Closely
behind that: a thicket of Run/Reset/Submit races on the Yaegi path
where a killed worker's stale rejection overwrites the next run's
result, and a Submit that grades against the *previous* run's stdout
because the input changed between Run and Submit.

## Findings

### F-1. Corrupt-progress backup writes one key per read (storage leak)
**Reproduce**:
1. `localStorage.clear()`
2. `localStorage.setItem('typeover:progress', 'not even json')`
3. Visit `/go/foundations/variables/01`
**Observe**: After hydration, `localStorage` contains 8
`typeover:progress:corrupt-<iso>` keys (verified). On
`/go/foundations/complete` the number balloons because
`ModuleCompleteCard` calls `getExerciseProgress(id)` for every
exercise in the module (≥58), and *each call* re-runs `read()`,
which backs up the still-unwritten corrupt blob until the first
`recordInstanceSeen` finally overwrites the original key.
**Expect**: Either (a) `read()` should back up exactly once and
immediately overwrite the corrupt key with `empty()`, or (b) the
backup write should be guarded by a "haven't backed THIS payload
up yet" check, or (c) cap the number of backups (e.g. keep last 3).
The current behaviour is an unbounded leak.
**Severity**: blocker

### F-2. Reset-while-running races the previous eval's rejection
**Reproduce**: In Freeform or FillBlankLineInput,
1. Type a long-running loop (e.g. `for {}`)
2. Click Run
3. Click Stop / reset runtime
4. Immediately click Run again on a valid program
**Observe**: There are two losing orderings:
- The terminated worker's pending Comlink call eventually rejects.
  The old `run()`'s `catch` block sets `runResult` to that error,
  **overwriting** the "Runtime was reset. Click Run again to try."
  sentinel `reset()` placed there.
- If the user re-Runs in step 4 fast enough, the new run completes
  successfully, and then the old rejection fires and overwrites the
  successful result with a stale error.
**Expect**: `useYaegiRun` should generation-tag pending runs (e.g.
an incrementing `runId`) and discard rejections / resolves whose
tag doesn't match the latest. `reset()` should bump that
generation.
**Severity**: major

### F-3. Submit after editing the input grades against stale Run result
**Reproduce**:
1. Open `/go/foundations/conditionals/07` (fill-line)
2. Type a *correct* answer
3. Click Run → wait for green pass
4. Edit the input box to garbage (`asdf`)
5. Click Submit (still enabled — `canSubmit` only requires
   `runResult !== null && !running && input.trim() !== ""`)
**Observe**: Submit succeeds and records `recordInstancePassed`
even though the current input does not match the canonical and
would not produce the expected stdout. The Feedback panel says
"Correct — your line produces the expected output." while the
RunResultPanel below shows stdout from the *previous* program.
**Expect**: `canSubmit` should track whether the *current* input
matches the input that produced the last `runResult`, or `setInput`
should clear `runResult` on edit. Freeform has the same defect
(edit textarea after Run, Submit, fake pass).
**Severity**: blocker

### F-4. `ModuleCompleteCard` triggers ~2N localStorage reads per render
**Reproduce**: View `/go/foundations/complete` with the full
58-exercise module passed.
**Observe**: Per `ModuleCompleteCard.onMount`: `summarizeTheme`
iterates `theme.exerciseIds` calling `getExerciseProgress(id)` for
each (one full `JSON.parse(localStorage.getItem(...))` per
exercise). The card *then* loops `theme.exerciseIds` again to
accumulate hint totals — another N reads. With 58 exercises and 6
themes that's **116 reads + 116 JSON.parse calls** for one card
render. Combined with F-1 this is catastrophic in a corrupt-state
scenario (corrupt blob → 116 backup-key writes per render).
**Expect**: Read once into a local snapshot, then aggregate. Same
applies to `ThemeProgressChip` / `ExerciseProgressChip` islands on
the theme overview, which each call `read()` independently.
**Severity**: major

### F-5. Share button is silent on most failure modes
**Reproduce**:
1. Complete a module (or set the progress blob accordingly)
2. Visit `/go/foundations/complete`
3. In DevTools: `Object.defineProperty(navigator,'share',{value:async()=>{throw new DOMException('denied','NotAllowedError')}})` and remove `clipboard`
4. Click Share
**Observe**: Zero feedback. No toast, no fallback panel, no console
hint. The `try/catch` in `ModuleCompleteCard.share()` lumps
*genuine* errors (permission denial, OS share-sheet crash, user
cancellation, clipboard rejection) all into `setShareState("idle")`,
which renders no message at all. The intended "Share unavailable —
copy this and paste it manually" fallback only fires when
`navigator.share` is *absent*, not when it *rejects*.
**Expect**: Distinguish cancellation (the only benign path) from
permission denial / generic error. On any non-cancel rejection,
fall back to the manual-copy panel.
**Severity**: major

### F-6. Manual-copy fallback drops the share URL
**Reproduce**: With no `navigator.share` and no `navigator.clipboard`,
click Share.
**Observe**: The error message displays only `shareText()` (the
prose) — the share URL that `clipboard.writeText` would have
included (`${text}\n${url}`) is nowhere on screen. Learners
manually copying lose the link to the celebration page.
**Expect**: Render both `shareText()` and `shareUrl()` in the
fallback so the learner has both halves to paste.
**Severity**: minor

### F-7. Glass style has no visible effect on Panel
**Reproduce**:
1. `/settings` → Style → Glass
2. Look at the live Preview, or any Panel anywhere on the site
**Observe**: `:root[data-style="glass"]` adds
`--panel-backdrop-filter: blur(10px) saturate(140%)` and a soft
drop shadow, but does **not** rebind `--color-bg-panel`. Panels
remain fully opaque, so `backdrop-filter` has nothing behind it to
blur. The Glass option is effectively a no-op — except for a
slight shadow change you'd miss without a side-by-side comparison.
The radio's description ("Translucent panels with subtle backdrop
blur where supported.") is therefore misleading.
**Expect**: Glass should set `--color-bg-panel` to a
`color-mix(... transparent)` value so the blur surface is real;
or update the description to be honest about what changes.
**Severity**: major

### F-8. Cardboard pattern is invisible on dark theme
**Reproduce**: Settings → Theme = Dark, Style = Cardboard.
**Observe**: The `--surface-pattern` radial-gradient stipple uses
`color-mix(in oklab, var(--color-fg-faint) 18%, transparent)`,
which lands at ~#5a5a5a × 0.18 ≈ near-black against the dark
panel background. The "warm paper grain" advertised by the picker
is undetectable in a screenshot.
**Expect**: Dark theme needs a brighter stipple colour (e.g. use
the warm accent rather than fg-faint), or the option should hide
itself under dark theme, or the description should note "best on
the Light theme".
**Severity**: minor

### F-9. Privacy notice doesn't mention `typeover:style`
**Reproduce**: Visit `/privacy`, search for "style".
**Observe**: The page enumerates `typeover:progress`,
`typeover:theme`, `typeover:density`, `typeover:radius`, and the
corrupt backup key — but `typeover:style` (added in iter 14) is
absent. The privacy section's own copy says "If anything on this
list stops being true … update this page in the same commit." It
didn't happen.
**Expect**: Add `typeover:style` to the list, and add an explicit
note about the unbounded `typeover:progress:corrupt-*` backup keys
(see F-1) once that bug is fixed.
**Severity**: minor

### F-10. Theme axis "System" doesn't react to live OS changes
**Reproduce**:
1. `/settings` → Theme → System
2. Toggle the OS appearance from Dark → Light (System Settings on
   macOS, etc.)
**Observe**: The page does not repaint. `setTheme("system")`
removes the pin and reads `osPreference()` *once* at the call
site; there is no `matchMedia(...).addEventListener('change', …)`
hooked up anywhere. Learner has to reload.
**Expect**: When the pin is absent (system mode), subscribe to
`prefers-color-scheme` changes and re-apply.
**Severity**: minor

### F-11. MCQ Enter-to-submit doesn't work; ArrowDown silently commits a new choice
**Reproduce**:
1. `/go/foundations/variables/01`
2. Tab to a radio, press Space to select the correct one (`score := -1`)
3. Press Enter
**Observe**: Nothing happens. Submit doesn't fire because there is
no form, and the MCQ doesn't intercept Enter. The learner has to
Tab forward to reach Submit. Worse: if they press ArrowDown
expecting "move focus to Submit", the **native radio group
re-selects the next radio** (which then *replaces* their chosen
answer with the wrong one), without any visible "are you sure"
moment.
**Expect**: Wire Enter on the radio group (or globally inside the
exercise panel) to `phase.submit()` when `canSubmit`. Optionally
treat arrow-key navigation as focus-only rather than
selection-commit (`role="radiogroup"` + `tabindex=-1` siblings),
to avoid the "I touched arrow and now I've changed my answer"
trap.
**Severity**: major

### F-12. Focus is dropped to `<body>` after MCQ submit
**Reproduce**: Pick an option, Tab to Submit, press Enter.
**Observe**: `document.activeElement` jumps back to `<body>` (or
the doc root) after the phase transitions to "wrong"/"right" and
the Submit button is removed from the toolbar. Screen-reader and
keyboard-only users lose their place; they have to Tab from the
top of the page to reach Try-again / Reveal correct / Next
exercise.
**Expect**: On phase transition, move focus to the Feedback panel
(role="status") or the primary next-action button (Try again /
Next exercise). Same applies after a successful FillBlankWord /
FillBlankLineInput / Freeform submit.
**Severity**: major

### F-13. MobileKeyBar overlays the Submit button at mobile widths
**Reproduce**: Resize browser to ≤390px, open
`/go/foundations/functions-and-multi-return/10` (a freeform),
scroll until you can see the Submit button.
**Observe**: The fixed `position: fixed; bottom: 0; z-index: 50`
bar covers the bottom ~44px of the viewport. There is no
`padding-bottom` on `<body>` (or the exercise main) to offset it,
so the Submit button at the natural end of the exercise sits
behind the bar. Learners have to scroll the page past its natural
end to reveal Submit, or notice the half-visible button under the
bar and tap blind.
**Expect**: Add `padding-bottom: <bar-height>` to the layout (or
the exercise container) at the same media-query break the bar
turns on.
**Severity**: major

### F-14. MobileKeyBar adds 17 buttons to the keyboard tab order
**Reproduce**: At mobile width, focus the freeform textarea, Tab.
**Observe**: The first Tab takes you into the bar's first button
("Tab" — which inserts two spaces). Each subsequent Tab moves
through the 16 remaining bar buttons (plus Run) before reaching
anything else on the page. A learner with a Bluetooth keyboard on
a tablet has to Tab through 17 buttons to escape the bar.
**Expect**: Tabindex the bar's buttons out of the natural order
(`tabindex="-1"`) since they're discoverable by sight on the bar
anyway and they're only useful from a thumb-tap. Or hide the bar
entirely when a hardware keyboard is detected (you can probe via
`mediaQuery("(pointer: fine)")`).
**Severity**: minor

### F-15. ExerciseShell footer RevealButton is silent (no failure record)
**Reproduce**:
1. Open any MCQ
2. Don't pick anything yet
3. Click "Show canonical" in the footer
4. Observe `localStorage`'s progress slot for that exercise
**Observe**: `hintsUsedTotal`, `instancesFailed`, `instancesPassed`
all stay at 0. The footer RevealButton in `ExerciseShell.tsx`
(line 176) has no `onReveal` wired, so peeking before submitting
is *completely* free of consequence — meanwhile the wrong-phase
"Reveal correct" button DOES record a failure. The two reveals
have indistinguishable visuals but very different progress
semantics. A learner gaming the system uses the footer button;
an honest learner who reveals after a wrong attempt eats the
failure.
**Expect**: Either record a hint-equivalent on footer-reveal
(once per exercise instance), or remove the footer reveal in
favour of the inline reveal already used by fill-line / freeform,
or document the asymmetry in design-docs/12.
**Severity**: minor (semantically major, but unlikely to be exploited
in v0 with no leaderboard)

### F-16. Wrong-pattern matcher is case-sensitive (but learners aren't)
**Reproduce**: On a fill-line exercise with a known distractor like
`'user := lookup(id); if user != nil { greet(user) }'`, type the
same line with a capital letter the learner often types
out of TS habit (e.g. `'User := lookup(id); …'` or
`'var doubled = count * 2'` vs distractor `'Var doubled = count * 2'`).
**Observe**: `normalise()` collapses whitespace but does not
lowercase. A capital-letter typo that *should* match an authored
distractor (and trigger the helpful `explain` text) instead falls
through to the generic "Not the expected output yet" message —
even though the Go compiler error the learner gets back is *also*
unhelpful for the wrong reason. Wrong-pattern guidance evaporates
exactly when it would be most useful.
**Expect**: For wrong-pattern matching only (not for the
correctness oracle), lowercase the comparison. Authored distractor
text remains the user-facing display.
**Severity**: minor

### F-17. Pasting a 10k-line program is silently accepted (and DiffView will choke)
**Reproduce**:
1. Open a Freeform exercise
2. Programmatically paste a 128KB program (verified via the test
   harness: 10000 lines of `// line N`)
3. Press "Show canonical" to open InlineCanonicalReveal
**Observe**: The textarea accepts the paste without complaint.
Subsequent calls to `InlineCanonicalReveal` re-evaluate `props.
submission()` which returns 128KB on every read, and DiffView
runs the `diff` library against a ~150-byte canonical — a
~128KB × N comparison that will jank or freeze the main thread.
Yaegi will also receive 128KB of Go source on Run.
**Expect**: Cap submission length at a sensible limit (e.g. 10KB)
with a friendly "Trim your code to under 10 KB to Run" message;
either truncate the diff source on the canonical-reveal path or
debounce / off-thread the diff.
**Severity**: minor (no current learner will hit this; bot or
mischievous user will)

### F-18. Theme axis is set globally before any Solid island even mounts
**Reproduce**:
1. Set `localStorage.setItem('typeover:theme','💀')`
2. Reload
**Observe**: The bootstrap script in BaseLayout (lines 36–77) only
accepts the four valid radius values etc., so the malformed value
falls through to default — *good*. But the bootstrap also does
*not* clear the malformed pin. The settings page next renders the
"System" radio as currently-active (because `currentChoice()`
filters unknowns to "system") while `localStorage` still holds
`💀`. Picking System again happens to remove it, but any other
pick keeps the pin around.
**Expect**: When the bootstrap rejects an invalid value, also
`localStorage.removeItem(key)` so the pin doesn't quietly persist
across the user's lifetime.
**Severity**: nit

### F-19. ModuleCompleteCard's `client:only="solid-js"` renders nothing on hydration failure
**Reproduce**:
1. Throttle network / corrupt Vite's optimised-dep cache (this
   happens organically; we saw it twice in this session with
   multiple dev servers fighting over `node_modules/.vite`)
2. Visit `/go/foundations/complete`
**Observe**: The static shell renders the heading "Module
complete" and the lede paragraph, but the `<Panel>` body — which
is entirely `client:only` — stays empty. No "couldn't load"
fallback, no skeleton, no error boundary. The celebration screen
looks like a dead page.
**Expect**: Provide a server-rendered fallback string or
`<noscript>` content. (`client:only` doesn't render server-side,
but you can wrap the island in an Astro slot that ships a
placeholder.) Same applies to all `client:only` islands —
AppearancePicker, ExerciseProgressChip, ThemeProgressChip,
FillBlankLineInput, Freeform — but the completion page is the
worst because the URL is going to land in someone's social share.
**Severity**: major

### F-20. ExerciseProgressChip / ThemeProgressChip don't react to other components' writes
**Reproduce**:
1. Open `/go/foundations/variables` (theme overview with multiple
   chips)
2. In another tab, open `/go/foundations/variables/01` and pass it
3. Switch back to the first tab
**Observe**: The chip for exercise 01 still says "not started"
until the page is reloaded. localStorage's `storage` event isn't
wired up, and there's no in-page pub/sub. Progress is read once
on mount.
**Expect**: Subscribe each chip to `window.addEventListener
('storage', …)` and re-read on the typeover:progress key. Bonus:
custom event on same-tab writes so multi-island pages update
without leaving the tab.
**Severity**: minor

### F-21. Empty themes mid-module silently lose the "Next exercise →" thread
**Reproduce** (will bite Module 2 ship):
1. Imagine a module where theme A has exercises, theme B has zero,
   theme C has exercises
2. Pass the last exercise of theme A
**Observe**: `firstExerciseOfNextTheme(...)` returns null because
theme B has no exercises. `lastExerciseInModule` is also null.
So `nextExerciseHref` falls through to undefined and the right-
phase falls back to "Back to theme overview", silently skipping
theme B entirely. The learner has no breadcrumb that there's an
empty theme between A and C, and no path forward from the
end-of-A page.
**Expect**: `firstExerciseOfNextTheme` should recurse to skip
empty themes; or the route should link to the empty theme's
overview page so the learner sees "coming soon" rather than
landing back where they started.
**Severity**: minor (latent; activates with Module 2)

### F-22. Curriculum index hard-codes "54 exercises" but actual count is 58
**Reproduce**: Visit `/`.
**Observe**: The TrackCard for Foundations reads "Module 1
(Foundations) ships 54 exercises across six themes" but
`find src/content/exercises/foundations -name '*.yaml' | wc -l`
returns 58. Static copy went stale relative to authored content.
**Expect**: Compute the number from `getCollection('exercises')`
filtered by module, or remove the count from the prose.
**Severity**: minor

### F-23. AppearancePicker's "initial" prop is a hardcoded value the radio sometimes lies about
**Reproduce**: Server-side render is hard to reach in dev, but
the bug is in the source. Each `RadioGroup` is instantiated with
`initial="system"` / `initial="normal"` / `initial="terminal"`.
Solid's first render uses this; `onMount` calls
`props.read()` to update. If `currentChoice()` returns a value
that DOESN'T match `initial` (typical — the user has set a pin),
the radio briefly renders with the wrong selection before
flipping. On a slow CPU the flicker is visible.
**Expect**: Render the radio group inside a `<Show
when={mounted()}>` so the picker waits for the read, OR move
the read out of `onMount` into the initial signal value. The
preview at the top doesn't have this issue because it reads no
state.
**Severity**: nit
